# TaskFlow

A small task management REST API for learning Java and Spring Boot. Create, read,
update, delete, and filter tasks. The project uses a Controller → Service → Repository
structure, with no authentication, frontend, or microservices.

## Stack

- Java 21
- Spring Boot 4.1.1
- Maven 3.9.11 through the included Maven Wrapper
- Spring Web MVC, Spring Data JPA, and Jakarta Validation
- H2 for immediate local use; an optional PostgreSQL profile
- JUnit, Mockito, and Spring MockMvc for tests

## Run locally

Install **JDK 21** and make sure `java -version` reports Java 21. Set `JAVA_HOME`
to your JDK directory if necessary. You do not need to install Maven or a database.
The first Wrapper run needs internet access to download Maven and dependencies.

From the project directory:

```bash
./mvnw spring-boot:run
```

On Windows, use `mvnw.cmd` instead (for example, `.\mvnw.cmd spring-boot:run` in PowerShell).
The Bash curl examples below also work in Git Bash or WSL.

The API is available at `http://localhost:8080/api/tasks`. To check it:

```bash
curl -i http://localhost:8080/api/tasks
```

An empty database returns `200 OK` with `[]`. There is no page at `/`.
Stop the application with **Ctrl+C**.

H2 runs in memory and starts empty. **All H2 data is lost when the application stops.**
The H2 web console is not enabled. Use the API to inspect tasks.

If port 8080 is already in use:

```bash
./mvnw spring-boot:run -Dspring-boot.run.arguments="--server.port=8081"
```

## Task fields

| Field | Type | Rules |
| --- | --- | --- |
| `id` | integer | Generated by the database; returned in responses |
| `title` | string | Required, not blank, at most 200 characters |
| `description` | string or null | Optional, at most 2,000 characters |
| `status` | string | Required: `TODO`, `IN_PROGRESS`, or `DONE` |
| `priority` | string | Required: `LOW`, `MEDIUM`, or `HIGH` |

Status and priority values are case-sensitive. Send their names, not numbers.
There are no automatic status or priority defaults. Any listed status can be
changed to any other listed status.

## Endpoints

| Method | Path | Successful response |
| --- | --- | --- |
| `POST` | `/api/tasks` | `201 Created`, task JSON, and a `Location` header |
| `GET` | `/api/tasks` | `200 OK`, a JSON array ordered by ascending id |
| `GET` | `/api/tasks/{id}` | `200 OK`, task JSON |
| `PUT` | `/api/tasks/{id}` | `200 OK`, updated task JSON |
| `DELETE` | `/api/tasks/{id}` | `204 No Content`, empty body |

`GET /api/tasks` accepts optional `status` and `priority` query parameters.
When both are provided, a task must match **both**. No matches returns `[]`,
not an error. The list is deliberately unpaginated for this small project.

`PUT` replaces all editable fields: send `title`, `status`, and `priority`
every time. Omitting `description` (or sending `null`) clears it. Updating a
missing task returns `404`; it does not create a task. Deleting a missing or
already deleted task also returns `404`. Partial updates with `PATCH` are not supported.

## Curl walkthrough

These examples assume a fresh application. If the created id is not `1`, replace
`1` in later commands with the id returned by your create request.

### Create a task

```bash
curl -i -X POST http://localhost:8080/api/tasks \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Learn Spring Boot",
    "description": "Build the TaskFlow API",
    "status": "TODO",
    "priority": "HIGH"
  }'
```

Response: `201 Created`, with `Location: /api/tasks/1` and:

```json
{
  "id": 1,
  "title": "Learn Spring Boot",
  "description": "Build the TaskFlow API",
  "status": "TODO",
  "priority": "HIGH"
}
```

### List, filter, and read

```bash
curl -i http://localhost:8080/api/tasks
curl -i 'http://localhost:8080/api/tasks?status=TODO'
curl -i 'http://localhost:8080/api/tasks?priority=HIGH'
curl -i 'http://localhost:8080/api/tasks?status=TODO&priority=HIGH'
curl -i http://localhost:8080/api/tasks/1
```

Quote URLs containing `&` so the shell treats the whole URL as one argument.

### Update a task

```bash
curl -i -X PUT http://localhost:8080/api/tasks/1 \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Learn Spring Boot",
    "description": "CRUD and tests finished",
    "status": "DONE",
    "priority": "MEDIUM"
  }'
```

### Delete a task

```bash
curl -i -X DELETE http://localhost:8080/api/tasks/1
```

Response: `204 No Content`. Reading the same task afterwards returns `404 Not Found`.

## Validation and errors

Errors use Spring's `ProblemDetail` JSON format with the content type
`application/problem+json`. Validation errors also include an `errors` object
mapping field names to messages.

```bash
curl -i -X POST http://localhost:8080/api/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":" ","status":"TODO","priority":"HIGH"}'
```

Response: `400 Bad Request`:

```json
{
  "title": "Bad Request",
  "status": 400,
  "detail": "Request validation failed",
  "instance": "/api/tasks",
  "errors": {
    "title": "Title is required"
  }
}
```

| Status | Meaning |
| --- | --- |
| `400 Bad Request` | Invalid fields, malformed/missing JSON, invalid enum names, or a non-integer id |
| `404 Not Found` | The requested task does not exist |
| `405 Method Not Allowed` | Unsupported method, such as `PATCH` |
| `415 Unsupported Media Type` | A request body is sent with an unsupported content type |
| `500 Internal Server Error` | Unexpected server error; details are logged on the server |

Use `Content-Type: application/json` for both `POST` and `PUT`.

## Tests and packaged application

```bash
# Run all tests
./mvnw test

# Clean, test, and build an executable JAR
./mvnw clean verify

# Start that JAR
java -jar target/taskflow-0.0.1-SNAPSHOT.jar
```

- `TaskServiceTest` uses Mockito to test service behavior without starting Spring
  or a database. It covers create/read/update/delete, missing tasks, and all filter branches.
- `TaskApiIntegrationTest` starts the Spring application context with a separate H2
  test database and sends requests through MockMvc. It checks persistence, HTTP status
  codes, the `Location` header, filtering, validation boundaries, invalid requests,
  and that a rejected update leaves the stored task unchanged.

Tests need neither PostgreSQL nor an already running application. MockMvc does not
occupy a network port. Test data is cleared before each integration test.
Mockito uses its interface-only proxy mock maker (configured in `src/test/resources/mockito-extensions/`)
because the only mocked dependency is `TaskRepository`.

## Optional PostgreSQL

Install and start PostgreSQL. As a database administrator, create a user and database
(replace the example password):

```sql
CREATE USER taskflow WITH PASSWORD 'change-me';
CREATE DATABASE taskflow OWNER taskflow;
```

Then, in the shell where you start TaskFlow:

```bash
export DB_URL='jdbc:postgresql://localhost:5432/taskflow'
export DB_USERNAME='taskflow'
export DB_PASSWORD='change-me'
./mvnw spring-boot:run -Dspring-boot.run.profiles=postgres
```

Or use the packaged JAR after exporting the same variables:

```bash
java -jar target/taskflow-0.0.1-SNAPSHOT.jar --spring.profiles.active=postgres
```

`DB_URL` and `DB_USERNAME` default to the values shown above; `DB_PASSWORD` is required.
The PostgreSQL driver is already included. PostgreSQL data survives application restarts.
This project does not automatically load `.env` files; export variables in your shell
or configure them in your IDE's run configuration. Do not commit real credentials.

The `postgres` profile uses Hibernate's `ddl-auto=update` to create/update tables for
learning. A production application would use explicit migrations, such as Flyway or
Liquibase, and a more restrictive schema setting. Running without the `postgres`
profile uses H2 again.

## How the code fits together

```text
src/main/java/com/example/taskflow/
├── TaskFlowApplication.java       Application entry point
├── controller/TaskController.java HTTP routes, request validation, status codes
├── service/TaskService.java       Task operations and transaction boundaries
├── repository/TaskRepository.java Database access through Spring Data JPA
├── model/                        Task entity, TaskStatus, TaskPriority
├── dto/                          TaskRequest and TaskResponse records
└── exception/                    Not-found exception and shared error handling

src/main/resources/
├── application.properties          Default H2 configuration
└── application-postgres.properties Optional PostgreSQL configuration

src/test/                           Service unit tests and API integration tests
```

Follow a request from `TaskController` to `TaskService` to `TaskRepository`.
The controller deals with HTTP. The service chooses the operation and controls
transactions. The repository reads and writes `Task` entities; Spring Data implements
its query methods from their names.

DTO means **Data Transfer Object**. The two DTO records describe JSON input and output
without exposing the persistence entity directly. A Java record is a concise way to
hold immutable data. `@Valid` checks the request's Jakarta Validation annotations
before calling the service. `GlobalExceptionHandler` turns exceptions into HTTP errors.

The project uses constructor injection, ordinary getters/setters, and explicit mapping
so that you can follow the code without Lombok, mapper libraries, or generic base services.

Useful references: [Spring Boot documentation](https://docs.spring.io/spring-boot/),
[Spring Data JPA query methods](https://docs.spring.io/spring-data/jpa/reference/jpa/query-methods.html),
and [Spring error responses](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html).
